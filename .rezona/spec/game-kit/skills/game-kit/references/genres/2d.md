# 2D Games — Layered Guidance

This file is best-practice guidance for 2D web games, layered from rendering
fundamentals up to genre-specific mechanics. It is not a platform contract —
see `contracts/global.md` for the rules you must not break. Use only the
layers relevant to the current brief; skip what the game does not need.

The template ships foundation helpers under `src/engine/` (loop, input,
canvas sizing, audio unlock). Use them instead of re-implementing this
plumbing; delete any file you don't use. They carry no game shape.

## Layer 1 — Rendering Foundation

Two viable rendering approaches; pick based on what the brief needs, not by default:

- **Canvas 2D** — the default choice for anything with continuous motion, many
  moving pieces, particle effects, or pixel-level drawing (platformers, shooters,
  physics toys, anything with dozens of independently moving sprites).
- **DOM + CSS** — simpler and often better for card games, board games, puzzle
  grids, or turn-based games where pieces are discrete elements with few
  simultaneously animating at once. Absolute-positioned `div`s with CSS
  transitions/transforms can out-perform a naive canvas re-draw for these
  shapes and are easier to make accessible.

If you choose Canvas 2D, `src/engine/canvas2d.ts` handles device-pixel-ratio
sizing — after it runs, draw everything in CSS pixel coordinates:

```tsx
const canvasRef = useRef<HTMLCanvasElement>(null)
const sizeRef = useCanvas2d(canvasRef) // { w, h } in CSS px — read inside the loop
```

- Never call `ctx.setTransform(...)` yourself — it wipes the ratio transform.
  For a scrolling camera, compose on top:
  `ctx.save(); ctx.translate(-cam.x, -cam.y); /* draw world */ ctx.restore()`.
- Clear-and-redraw the full frame each tick unless profiling shows a real
  cost; partial invalidation is a premature optimization for most 2D games.

**Pixel art**: crispness is a one-liner people forget — set
`canvas { image-rendering: pixelated }` (CSS) and draw sprites at integer
positions/scales (`Math.round`), or the art blurs and shimmers. Keep sprite
source sizes power-of-two-ish and scale by whole factors (2x, 3x).

For a library instead of raw Canvas 2D (worthwhile once a scene has hundreds of
sprites, needs a scene graph, or wants built-in sprite batching), PixiJS is the
standard choice for 2D web games — add it via the dependency script (see
SKILL.md). Do not add it by default.

## Layer 2 — Game Loop & State Architecture

`src/engine/loop.ts` drives the loop with `requestAnimationFrame` and passes a
real delta time (seconds, clamped) so gameplay speed is independent of frame rate:

```tsx
useGameLoop((dt) => {
  update(stateRef.current, inputRef.current, dt) // simulate
  render(ctx, stateRef.current, sizeRef.current) // draw
})
```

Keep gameplay state OUT of React state. React re-renders are not free and most
2D games tick 60 times a second; put entities in a plain object or class held
in a `ref`, mutate it in the loop, and only touch `useState` for things the UI
actually needs to re-render for (score display, HUD text, phase banners).

```tsx
class GameState {
  entities: Entity[] = []
  score = 0
  phase: 'title' | 'active' | 'ended' = 'title'
  update(dt: number, input: InputState) { /* mutate entities in place */ }
}

function App() {
  const gameRef = useRef<GameState>()
  if (!gameRef.current) gameRef.current = new GameState()
  const [hud, setHud] = useState({ score: 0 }) // low-frequency HUD mirror only
  // ...
}
```

**Suggested file layout** — iteration turns ("make it faster / harder /
greener") should be a one-file edit in `config.ts`, not an archaeology dig:

```
src/
  engine/          # foundation helpers (loop/input/canvas2d/audio) — delete unused
  game/
    config.ts      # ALL tunables: speeds, spawn intervals, sizes, palette hexes, SPRITES metadata
    state.ts       # game state types + createInitialState()
    update.ts      # per-frame simulation: (state, input, dt) => void
    render.ts      # per-frame drawing: (ctx, state, size) => void
  App.tsx          # assembly: hooks + <canvas> + HUD overlay + screens
```

Small games may merge update/render into one file; the non-negotiable ideas
are "tunables live in config.ts" and "simulation is separate from drawing".

## Layer 3 — Input & Interaction

`src/engine/input.ts` unifies pointer + keyboard into one snapshot read once
per frame inside the loop (never inside a `useEffect` — refs there won't see
between-frame events):

```tsx
const { inputRef, handlers } = useInput() // spread `handlers` onto the root container

useGameLoop((dt) => {
  const input = inputRef.current
  if (input.keys.has('ArrowLeft')) player.x -= speed * dt
  // edge detection (tap/press-once) is a two-line pattern:
  const tapped = input.pointer.down && !prevDown.current
  prevDown.current = input.pointer.down
})
```

Keys hold `e.code` values (`'ArrowLeft'`, `'KeyW'`, `'Space'`) — layout
independent. The hook is single-pointer by design; games needing simultaneous
move+action touch zones (virtual joystick + buttons) write their own zoned
handlers — see `patterns/mobile-game-controls.md`. Do not add visible controls
the mechanic does not need.

## Layer 4 — Assets & Performance

- Preload images before showing gameplay; a broken/half-loaded sprite is worse
  than a brief loading state. Show the title screen immediately (rule 1 of the
  platform contract), load behind it, fade gameplay in when ready:

```tsx
function loadImage(src: string): Promise<HTMLImageElement> {
  return new Promise((resolve, reject) => {
    const img = new Image()
    img.onload = () => resolve(img)
    img.onerror = reject
    img.src = src
  })
}
// Batch-load everything a scene needs before entering it, not lazily mid-frame:
const images = await Promise.all(Object.entries(ASSETS).map(async ([k, src]) => [k, await loadImage(src)]))
```

- **Audio** — `src/engine/audio.ts` wraps Web Audio and handles the mobile
  unlock landmine (browsers keep `AudioContext` suspended until a user
  gesture; without the unlock, iOS games are silently mute forever):

```tsx
useEffect(() => {
  void audio.load('hit', ASSETS.sfx_hit)
  void audio.load('theme', ASSETS.bgm_theme)
  audio.playBgm('theme', { volume: 0.4 }) // queued until the first tap/keypress
}, [])
// in gameplay: audio.playSfx('hit')
```

  What to generate and at what length/volume: `patterns/asset-pipeline.md`.

- **Sprite sheets** beat many small images for anything with more than a
  handful of frames. Keep slicing metadata in `config.ts` and draw with a
  source-rect — this is the canonical helper (the `gen-sprite-animation`
  skill, when available, produces sheets matching it):

```ts
export const SPRITES = {
  hero_walk: { cols: 3, rows: 3, frames: 9, fps: 10 },
} as const

function drawFrame(
  ctx: CanvasRenderingContext2D, img: HTMLImageElement,
  meta: { cols: number; rows: number; frames: number },
  frame: number, x: number, y: number, w: number, h: number,
) {
  const i = frame % meta.frames
  const fw = img.naturalWidth / meta.cols
  const fh = img.naturalHeight / meta.rows
  ctx.drawImage(img, (i % meta.cols) * fw, Math.floor(i / meta.cols) * fh, fw, fh, x, y, w, h)
}
// frame index advances on time, not ticks: Math.floor(elapsed * meta.fps)
```

- Reuse offscreen canvases for static/expensive-to-redraw layers (backgrounds,
  tilemaps) instead of redrawing them every frame; only invalidate when the
  content actually changes. **Parallax** is the cheapest depth you can buy:
  2-3 offscreen layers translated at factors like 0.2 / 0.5 / 1.0 of camera x.

## Layer 5 — Genre-Specific Mechanics

- **Collision detection** — AABB (`ax < bx+bw && ax+aw > bx && ay < by+bh && ay+ah > by`)
  covers most arcade/platformer needs; circle-vs-circle (`distance < r1+r2`) for
  anything round. Only reach for a physics library (e.g. `matter.js`) when the
  brief needs realistic stacking, rotation, or constraint-based physics —
  most games do not.
- **Platformers** — resolve horizontal and vertical movement separately per
  tick (resolve X, then Y) so slopes/corners don't tunnel; apply gravity as a
  velocity accumulator (`vy += gravity * dt`), not a position offset. Jump
  buffering and coyote time turn "correct" jumping into "fair" jumping — see
  `patterns/game-feel.md` → Controls feel.
- **Top-down movement** — normalize the input direction vector before scaling
  by speed, or diagonal movement is faster than cardinal movement.
- **Tile maps** — store the map as a 2D array of tile IDs, render only the
  tiles that intersect the current viewport, and look up collision by
  converting world position to tile-grid coordinates (`Math.floor(x / tileSize)`)
  rather than testing every tile every frame.
- **Waves/spawning** — drive enemy/obstacle spawns off elapsed time or score
  thresholds, not frame count, so difficulty pacing is frame-rate independent.
  Ramp formulas and pacing targets: `patterns/game-feel.md` → Difficulty pacing.
- **Juice** (screen shake, hit-stop, particles, floating text, transitions) is
  what separates "works" from "feels alive" — recipes live in
  `patterns/game-feel.md`; pick the 3-5 that fit the mechanic.

## Delivery Checklist

1. First frame shows brief-specific content — no leftover `SCAFFOLD-PLACEHOLDER` text.
2. The chosen rendering approach (Canvas vs DOM) matches the mechanic's actual needs.
3. Gameplay state lives outside React state; only HUD-relevant values trigger re-renders.
4. Every device-only input path has a touch/mouse/keyboard fallback (see `contracts/global.md`).
5. If the game can reach an "ended" state, the player can restart without a page refresh.
6. `index.html` `<title>` is the game's real name, not the scaffold title.
7. The title screen is poster-quality and something on it moves (it feeds the cover capture).
8. Every core action gives visible AND audible feedback (`patterns/game-feel.md` checklist).
9. Tunables (speeds, spawn rates, palette) are centralized in `src/game/config.ts`.
