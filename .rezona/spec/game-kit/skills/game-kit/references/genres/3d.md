# 3D Games — Layered Guidance

This file is best-practice guidance for 3D web games, layered from rendering
fundamentals up to genre-specific mechanics. It is not a platform contract —
see `contracts/global.md` for the rules you must not break. Use only the
layers relevant to the current brief; skip what the game does not need.

## Layer 1 — Rendering Foundation

three.js is the standard choice for 3D on the web — it is **preinstalled in
the template** (`three` + `@types/three`); import it directly. Other libraries
go through the dependency script (see SKILL.md). Two ways to use it; pick one
and stay consistent:

- **Vanilla three.js** — you own the scene graph, render loop, and object
  lifecycle directly. Best when the scene is imperative/procedural (physics-driven,
  many dynamically spawned objects) or when you want full control over the
  render loop's timing.
- **React Three Fiber (`@react-three/fiber`, optionally `@react-three/drei`
  for helpers)** — declare the scene as JSX; React reconciles it. Best when the
  scene is mostly static/declarative (fixed level geometry, a handful of
  animated objects) and you want the scene to compose naturally with React state.

Whichever you pick, **draw a hard ownership line and do not cross it**: React
owns UI overlays and app-level state (HUD, menus, config); three.js (or R3F's
own tree) owns the scene graph and the render loop. Do not let a React
re-render rebuild three.js objects (geometries, materials, the renderer) on
every state change — construct them once, mutate their properties in the loop.

Vanilla setup, called once from an effect that owns the canvas:

```tsx
function startGame(canvas: HTMLCanvasElement) {
  const renderer = new THREE.WebGLRenderer({ canvas, antialias: true })
  const scene = new THREE.Scene()
  const camera = new THREE.PerspectiveCamera(60, canvas.clientWidth / canvas.clientHeight, 0.1, 1000)
  camera.position.set(0, 5, 10)

  const resize = () => {
    const { clientWidth: w, clientHeight: h } = canvas
    // Without an explicit pixel ratio the renderer stays at 1x and every
    // high-DPI phone/laptop renders BLURRY. Clamp at 2: full DPR on a
    // 3x phone triples the fill cost for no visible gain.
    renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2))
    renderer.setSize(w, h, false)
    camera.aspect = w / h
    camera.updateProjectionMatrix()
  }
  const ro = new ResizeObserver(resize)
  ro.observe(canvas)
  resize()

  let last = performance.now()
  renderer.setAnimationLoop((now: number) => {
    const dt = Math.min((now - last) / 1000, 1 / 30)
    last = now
    // update(dt) — mutate scene objects here
    renderer.render(scene, camera)
  })

  return {
    scene, camera, renderer,
    dispose() {
      renderer.setAnimationLoop(null)
      ro.disconnect()
      renderer.dispose()
    },
  }
}
```

In React, mount/unmount this exactly once per canvas:

```tsx
function App() {
  const canvasRef = useRef<HTMLCanvasElement>(null)
  useEffect(() => {
    if (!canvasRef.current) return
    const game = startGame(canvasRef.current)
    return () => game.dispose()
  }, []) // empty deps — never re-run this on unrelated state changes
  return <canvas ref={canvasRef} style={{ width: '100vw', height: '100dvh', display: 'block' }} />
}
```

Ship for mid-range mobile GPUs by default: keep polygon counts and texture
sizes modest, avoid unbounded dynamic lights, and always have a procedural
fallback (a colored primitive) so a failed asset load never blanks the scene.

### Scene look recipe

Bare three.js defaults produce the "gray plastic on black void" look. Five
settings, applied once at startup, are most of the distance between "thrown
together" and "intentional" — call this right after creating the renderer:

```ts
import { RoomEnvironment } from 'three/addons/environments/RoomEnvironment.js'

function applySceneLook(renderer: THREE.WebGLRenderer, scene: THREE.Scene) {
  // 1. Tone mapping — the single biggest switch: without it, lit scenes
  //    clip to flat white/black instead of rolling off like film.
  renderer.toneMapping = THREE.ACESFilmicToneMapping
  renderer.toneMappingExposure = 1.1
  // 2. Soft shadows from ONE key light (more shadow-casting lights = more cost).
  renderer.shadowMap.enabled = true
  renderer.shadowMap.type = THREE.PCFSoftShadowMap

  // 3. Background + fog in the SAME hue family — fog reads as depth; a
  //    mismatched fog color makes the horizon look cut out with scissors.
  scene.background = new THREE.Color('#1a2233')
  scene.fog = new THREE.Fog('#1a2233', 20, 90)

  // 4. Minimal light rig: hemisphere fill (sky/ground tint) + warm key.
  scene.add(new THREE.HemisphereLight('#bfd4ff', '#2a2018', 0.7))
  const key = new THREE.DirectionalLight('#fff2d8', 2.2)
  key.position.set(8, 14, 6)
  key.castShadow = true
  key.shadow.mapSize.set(1024, 1024) // mobile budget: never above 1024
  key.shadow.camera.far = 60
  scene.add(key)

  // 5. Environment lighting — PBR materials (metalness/roughness) only come
  //    alive with an environment to reflect; RoomEnvironment is free (no asset).
  const pmrem = new THREE.PMREMGenerator(renderer)
  scene.environment = pmrem.fromScene(new RoomEnvironment()).texture
}
```

Swap the three hex colors per the brief's mood (they are tunables — keep them
in `config.ts`). Post-processing (bloom etc.) stays OFF by default on mobile;
fog + tone mapping + one shadow buys most of the look for a fraction of the cost.
Ground the scene: give objects something to stand on (a floor plane receiving
the key light's shadow) — floating-in-void reads as unfinished.

## Layer 2 — Game Loop & State Architecture

Separate rendering (every frame, variable dt) from physics/logic (fixed
timestep) when using a physics engine — variable-step physics is not
deterministic and can tunnel through thin colliders at low frame rates:

```ts
const FIXED_DT = 1 / 60
let accumulator = 0

function onFrame(dt: number, world: RapierWorld) {
  accumulator += dt
  while (accumulator >= FIXED_DT) {
    world.step() // physics engine step — always the same size
    accumulator -= FIXED_DT
  }
  // render-only interpolation/camera follow can use the raw dt
}
```

For physics, **Rapier** (`@dimforge/rapier3d-compat`) is the standard choice
for web/WASM 3D physics — deterministic, fast, and works well with three.js
by copying rigid-body transforms onto mesh objects each frame. Hand-rolled
physics (simple gravity + AABB/sphere checks) is fine for games that don't
need real rigid-body stacking or constraints.

Keep per-entity gameplay data in plain objects/classes outside React state,
same principle as 2D: React re-renders should not be in the hot path.

**Suggested file layout** — tunables in one place makes iteration turns cheap:

```
src/
  engine/          # foundation helpers — input/audio work for 3D too; delete unused
  game/
    config.ts      # ALL tunables: speeds, spawn rates, palette/light hexes, camera params
    state.ts       # game state types + createInitialState()
    scene.ts       # scene assembly (startGame, applySceneLook, object builders)
    update.ts      # per-frame simulation: (state, input, dt) => void
  App.tsx          # assembly: canvas mount effect + HUD overlay + screens
```

## Layer 3 — Input & Interaction

The template's `src/engine/input.ts` (pointer + key snapshot) and
`src/engine/audio.ts` (unlock + SFX/BGM) work for 3D games unchanged — only
the render loop differs (`renderer.setAnimationLoop`, not `useGameLoop`).
Read the snapshot inside the animation loop via the ref.

- **Camera control** — pick one mode per game and commit: orbit (mouse
  drag/pinch to rotate around a target — `OrbitControls` from `three/examples`
  or drei's `<OrbitControls>`), first-person (pointer-lock + WASD, desktop-only
  unless you also support touch look), or fixed/scripted (camera follows a
  target on rails, no player camera control — the simplest and most
  mobile-friendly default for action/adventure games).
- **Touch**: separate the look/rotate gesture from the movement gesture — a
  single touch drag cannot mean both at once. A common split is a virtual
  joystick (bottom-left) for movement and drag-anywhere-else for camera look;
  see `patterns/mobile-game-controls.md`.
- **Picking objects in 3D from a 2D pointer event** — raycast from the camera
  through the pointer's normalized device coordinates:

```ts
function pickObject(event: PointerEvent, canvas: HTMLCanvasElement, camera: THREE.Camera, scene: THREE.Scene) {
  const rect = canvas.getBoundingClientRect()
  const ndc = new THREE.Vector2(
    ((event.clientX - rect.left) / rect.width) * 2 - 1,
    -((event.clientY - rect.top) / rect.height) * 2 + 1,
  )
  const raycaster = new THREE.Raycaster()
  raycaster.setFromCamera(ndc, camera)
  return raycaster.intersectObjects(scene.children, true)[0]?.object ?? null
}
```

## Layer 4 — Assets & Performance

- Load models with `GLTFLoader` (glTF/`.glb` is the standard interchange
  format for web 3D — prefer it over `.obj`/`.fbx` for anything beyond a
  static prop). Load textures with `THREE.TextureLoader`; set
  `texture.colorSpace = THREE.SRGBColorSpace` for color textures so they
  don't render washed out.
- **Generated models** (`submit_model3d_generation` → `.glb` under
  `src/assets/`) import through `assets.ts` like any asset — the template
  declares `*.glb` modules, so a plain import yields the bundled URL. They
  arrive at arbitrary scale/origin; normalize before use:

```ts
import { GLTFLoader } from 'three/addons/loaders/GLTFLoader.js'

async function loadModel(url: string): Promise<THREE.Object3D> {
  const gltf = await new GLTFLoader().loadAsync(url)
  const model = gltf.scene
  const box = new THREE.Box3().setFromObject(model)
  const size = box.getSize(new THREE.Vector3()).length()
  model.scale.multiplyScalar(3 / size)  // fit into a ~3-unit sphere
  box.setFromObject(model)
  model.position.y -= box.min.y          // feet on the ground plane
  model.traverse((o) => {
    if ((o as THREE.Mesh).isMesh) { o.castShadow = true; o.receiveShadow = true }
  })
  return model
}
```

  If the file ships animation clips, create one `AnimationMixer` when the model loads,
  play the selected clip, and update that mixer from the render loop:

```ts
const mixer = new THREE.AnimationMixer(model)
const clip = gltf.animations[0]
if (clip) mixer.clipAction(clip).play()

renderer.setAnimationLoop(() => {
  const dt = clock.getDelta()
  mixer.update(dt)
  renderer.render(scene, camera)
})

// When replacing or removing the model:
mixer.stopAllAction()
mixer.uncacheRoot(model)
```

  Do not recreate or replay the mixer on every React render. Keep the colored-primitive
  fallback: a failed load must degrade, never blank the scene.
- Reuse geometries and materials across instances (`InstancedMesh` for many
  copies of the same object — trees, crowd members, bullets) instead of
  cloning a full mesh per instance; each unique material/geometry pair is a
  separate draw call.
- Dispose what you create: call `.dispose()` on geometries, materials, and
  textures when an object is removed, or memory grows unbounded over a play
  session.
- Keep shadow maps and post-processing off by default on mobile; add them
  only if the brief specifically needs the look and you've confirmed it holds
  frame rate on a mid-range device.

## Layer 5 — Genre-Specific Mechanics

- **Character controller** — for anything other than a simple physics
  capsule, move the character in local space (forward/right relative to
  camera yaw) then apply the result to world position; do not move directly
  along world X/Z from raw input, or movement direction flips confusingly
  when the camera turns.
- **Level/scene organization** — group static level geometry under one
  `THREE.Group` you build once; keep frequently-changing objects (player,
  enemies, projectiles) as separate top-level objects so you're not
  re-traversing static geometry to find dynamic ones.
- **Simple pathfinding** — for grid-like levels, A* over a coarse
  walkability grid is enough for most games; do not reach for a full
  navmesh solution unless the brief needs organic, non-grid terrain
  navigation.
- **Camera follow** — lerp the camera position/lookAt toward the target
  each frame (`camera.position.lerp(desiredPos, 1 - Math.pow(0.001, dt))`)
  rather than snapping, so camera motion reads as smooth rather than jittery.

## Delivery Checklist

1. First frame shows brief-specific content — no leftover placeholder torus/box.
2. React never rebuilds three.js scene objects on re-render; the render loop
   is created once and disposed once.
3. Camera control mode matches the mechanic and works on both touch and desktop.
4. A failed asset load degrades to a procedural placeholder, never a blank scene.
5. Physics (if used) steps on a fixed timestep, decoupled from render dt.
6. Pixel ratio is clamped (`setPixelRatio(min(devicePixelRatio, 2))`) — no blurry retina render.
7. Tone mapping, fog, and lights are deliberately set (scene look recipe), not three defaults.
8. `index.html` `<title>` is the game's real name; title screen is poster-quality with motion.
9. Every core action gives visible AND audible feedback (`patterns/game-feel.md` checklist).
10. Tunables (speeds, palette/light hexes, camera params) are centralized in `src/game/config.ts`.
